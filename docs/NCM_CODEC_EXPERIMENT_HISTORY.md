# NCM codec experiment history

Last updated: 2026-11-11. This is a working history of experiments and their tradeoffs. A result recorded here is not a final-solution checkpoint. The final-solution checkpoint section remains in [the DeepSeek codec plan](DEEPSEEK_NCM_CODEC_PLAN.md) and is reserved for verified solutions, as requested.

Results below come from terminal output shared in the project conversation and repository reports/scripts. The Linux run artifacts are on the training computer; they are not part of this checkout. A dash means that a comparable result was not available in the conversation, not that the test failed. Record the report path and checkpoint whenever possible.

## What we are trying to improve

The VQ-VAE codec takes tokenized C# text and reconstructs it through discrete VQ codes. We want accurate, usable reconstruction and a representation that a later NCM generator can predict economically. These experiments evaluate the codec, not the coding ability or speed of a trained generator. The longer-term goal also includes Godot/game development; the current compile tests use a minimal C# harness and Vector2 stub, not the Godot engine or behavioral tests.

Token accuracy measures individual positions; exact match requires all compared token IDs to match. Character similarity is descriptive. Compilation checks that a snippet builds in the test harness; it can pass even if a method is renamed or behavior changes. The 48-method stress set has been used repeatedly during development, so it is a development benchmark, not an untouched final test.

## Stable conclusions and open questions

- The current 64-level codec is more accurate than the compact runs tested here, but its fixed-width representation is very large and 20 of 48 stress reconstructions fail to compile. The 8- and 16-level compact runs compiled none of those stress outputs without corrections.
- Identifier and expression corruption remains a visible failure mode. A method can compile with a changed identifier, so compilation cannot replace exact reconstruction or behavioral checks.
- A correction sidecar can restore known input, but it requires original token IDs. A generator cannot obtain an unknown target's corrections for free. A pointer/copy mechanism could copy text actually present in its input; the current four-example pilot validation showed 8/34 exact identifier occurrences in prompts, too small a sample to assess general utility.
- The selected DeepSeek tokenizer and 64 levels were prior working choices; the size and compact-run results are evidence to consider when selecting the final design. They do not establish a final solution.
- Documentation was excluded from the later codec corpus by request. Whether and how to introduce documentation to a generator or retrieval system remains separate work.
- The 48 stress snippets and repeatedly used validation splits have informed design choices. A larger independent test set and behavioral checks are needed before a final quality claim.

## Pending GPU speed changes

Quantizer utilization counters are transferred from GPU to CPU together instead of per level. The short screen below compares AOTriton on/off and BF16, but does not establish final quality or isolate the counter optimization's effect. Existing running processes do not pick up changed code or environment. ## Research: paths beyond tuning codec settings

See [VQ position reduction research](VQ_POSITION_REDUCTION_RESEARCH.md) for the subsequent focused investigation of compact latent representations, adaptive allocation, quantization methods and later lossless index coding.

Research reviewed 2026-11-12, while the identifier-weight experiment was in progress. These are candidate directions, not claims that our model already implements them.

- [Latent Programmer](https://research.google/pubs/latent-programmer-discrete-latent-codes-for-program-synthesis/) is directly related: it trains a discrete autoencoder on program outputs, predicts latent codes from inputs, then generates a program. It reports program-synthesis gains in its own domains, not a guarantee of exact reconstruction or performance on this C#/Godot dataset. Its full generative pipeline is a useful architecture and evaluation reference.
- [Learning Better Lossless Compression Using Lossy Compression](https://openaccess.thecvf.com/content_CVPR_2020/html/Mentzer_Learning_Better_Lossless_Compression_Using_Lossy_Compression_CVPR_2020_paper.html) uses a lossy reconstruction plus entropy-coded residual for exact image recovery. Our token correction sidecar follows the same general idea but currently uses a simple position/token encoding, is a diagnostic rather than a complete production archive, and requires original target tokens. Applying learned residual coding to C# would need implementation and measured overhead.
- [Language Modeling Is Compression](https://arxiv.org/abs/2309.10668) explains how predictive distributions can drive a lossless entropy coder. A learned probability model and arithmetic coder could potentially reduce the bit cost of VQ codes or corrections, but require exact and reproducible encoder/decoder probabilities and consume compute. Entropy-coding a VQ code stream does not make its lossy decoder exact, reduce the number of code positions the generator must predict, or provide unknown target corrections.
- [CodeT5](https://aclanthology.org/2021.emnlp-main.685/) adds identifier-aware tagging and masked-identifier prediction in code model pretraining. Our occurrence-weighted reconstruction loss is different: it weights existing reconstruction positions. Identifier-aware objectives, controlled renaming augmentation and source-conditioned copying are hypotheses for NCM, not guaranteed exactness.
- [Synchromesh](https://arxiv.org/abs/2201.11227) reports retrieval and constrained decoding for program synthesis in SQL, Vega-Lite and SMCalFlow. Syntax, scope and type constraints or compiler feedback may help generated C#, but cannot guarantee behavior or restore arbitrary lost original names. Integrating constraints into our latent-code-first decoder is nontrivial and requires separate engineering and evaluation.

Proposed direction after the current short run: evaluate byte-exact input round trips, compressed latent/correction size and end-to-end speed separately from generated code quality; explore a source-conditioned copy path or identifier-aware reconstruction for available project text; test a latent-conditioned autoregressive/refinement decoder as an architectural hypothesis, measuring teacher-forced and free-running results plus latency. Preserve the existing 64-level benchmark while comparing any new architecture against a genuinely independent, file/template-held-out dataset. These approaches serve different purposes: no oracle correction or copied target may be used as if available at generation time. No evidence yet demonstrates 99% reconstruction, 48/48 generalization, compactness and fast generation simultaneously.
# Two-teacher codec screen (completed)

The paired 348-method comparison found 192 exact for both rare-only and repeated-piece weighting, 26 for rare-only, 32 for repeated-piece only, and 98 for neither. On the 48-item stress set, rare-only was exact on two examples the repeated model missed, while neither gained unique exact matches; each had two unique compilation passes. The 5k screen trained a fresh 64-level, width-192, encoder-8 student with the rare-only configuration plus a 0.1-weight auxiliary loss. Two frozen models taught their renormalized top-four token distributions only where their top prediction matched the known training target. Teacher compute was training-only; the result is a single codec.

The student achieved validation accuracy 98.28% and exact 38.31%. On 348 full methods it was exact on 219, versus 218 rare-only and 224 repeated-piece. Paired against rare-only, 27 were exact only for the student and 26 only for rare-only. On 48 stress snippets it achieved 98.80% token accuracy, 36 exact and 39 raw compiles, versus rare-only 98.92%, 39 exact and 39 compiles. The student did not establish a better single codec; the 5k screen has one run per configuration and these are repeatedly examined development sets. This does not demonstrate generator performance or reduce VQ index count.

Combining previously repaired rare-only results with already-compiled repeated and student candidates yielded no additional passes: 43/48 compiled and 40/48 were exactly equal as text. The five remaining snippets commonly lose identifiers across declarations and uses. A bounded diagnostic proposes parameter names from reconstructed signatures for compiler-reported undeclared names, and tries a limited body-keyword punctuation repair. This regex-based heuristic is not actual scope analysis and can silently change behavior, so compiling candidates require exactness and semantic evaluation. It is an ambiguity guard, not a correctness guarantee: unique compilation does not prove equivalence, and earlier retained compiler-only repairs also require evaluation.
